# Delegation Policy

主线程保留范围、验收标准、架构与公共接口、持久化数据、兼容性、安全、不可逆操作、跨工作流整合和最终验收。子代理只在已界定的范围内决定“怎么完成”；发现上述主线程决策时，应带着证据、选项和风险返回。

优先直接完成小而清楚的任务。只有子任务能独立产生有用证据、且不会丢失主线程上下文时才委派。调研、局部实现、测试和独立复核通常适合委派；困难且跨模块的判断留在主线程。

派发前：

1. 确认运行时实际支持的代理和并发能力，尊重用户指定的路线。
2. 划分互不重叠的写入范围；有重叠的写入必须串行。
3. 在任务中写清目标、完成证据、起始边界、保留给主线程的决定、允许改动的文件范围、验证要求和返回条件。
4. 对影响行为、跨模块、公共接口、数据、安全或部署的改动，要求独立验证；纯文案或确定性单文件配置可由执行者自检。

子代理回传必须以简短摘要开头：`pass`、`partial` 或 `blocked`；行为变化；实际变更路径；执行过的验证及结果；未决假设或 `none`。出现越界文件、跳过验证、证据矛盾或高风险边界时，主线程必须查看实际 diff 和证据后再接受结果。

默认最多并行三个互不依赖的工作流。对同一语义阻塞最多尝试三次；弱结果应更换路线或回到主线程，而不是反复重试。仍无法推进时，向用户报告已验证事实、可选方向、风险和需要的明确决定。
